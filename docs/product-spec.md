# 產品規格（草案）— EDB 掌握式學習平台

四個決策已定，這份把規則寫成可施工的形式。機器可讀的版本在
[`data/question-policy.json`](../data/question-policy.json)。

## 一、已定的四條

| | 決定 | 影響 |
| --- | --- | --- |
| a | **不固定 50 題** | 掌握 = 把該知識點的**整個題庫**答對；題數由類型決定 |
| b | **按知識點類型配額** | 均衡方案，數學共 **22,805 題** |
| c | **AI 審核**老師生成的題目 | 不上人手審批，靠自動規則 + 語言模型複審 |
| d | **學生 + 老師**可見作答 | 家長只看總分與薄弱點摘要 |

## 二、掌握規則

```
掌握 = 該知識點的題庫全部答對
```

- 重做時**只重出錯過的題**，避免學生為了刷分重複做已會的題。
- 但**第一次作答的正確率要另外記錄**。否則「重做到全對」會把真實掌握程度抹平——
  這是最容易做錯的一點。
- 每個知識點同時記三個數字：首次正確率、當前已答對題數／題庫總數、最後作答時間。

## 三、題量配額（均衡方案）

| 類型 | 題/點 | 點數 | 小計 | 理由 |
| --- | ---: | ---: | ---: | --- |
| procedural | 40 | 310 | 12,400 | 有明確算法，可換數字與情境 |
| conceptual | 20 | 222 | 4,440 | 問法有限，硬湊會變同義重複 |
| reasoning | 25 | 121 | 3,025 | 證明題要逐題設計 |
| application | 30 | 81 | 2,430 | 要貼香港情境，寫作成本高 |
| modeling | 15 | 34 | 510 | 每題一個完整情境 |
| **合計** | | **768** | **22,805** | 現有 3,215 題的 7.1 倍 |

按階段：

| P1 | P2 | P3 | P4 | P5 | P6 | S1–S3 | S4–S6 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,265 | 1,100 | 840 | 1,435 | 1,600 | 660 | 7,600 | 8,305 |

小學六級合計 **6,900 題**（222 個知識點）。

## 四、每道題要有甚麼

沿用現有 schema（`data/questions.json`），一個知識點的題目必須包含：

- `prompt` 題幹；`answer` 答案；`explanation` **逐步解說**（不是只寫答案）
- 數值題：`verify` 可獨立重算的表達式（腳本會核對，不等於 `answer` 就不入庫）
- 選擇題：`choices` 至少 2 個，`answer` 必須是選項之一
- 需要圖時：`figure` 內聯 SVG（有 `viewBox`、`currentColor`、不引外網）；
  圖形選項配 `hideChoiceText: true`
- 需要表時：目前**沒有表格支援**（現有 0 道題有表），要新增 `table` 欄位與前端渲染

## 五、老師課堂迴路

```
上傳筆記 → 解析 → 對到知識點 → 生成 10 題 → AI 審核 → 派發 → 學生作答 → 記錄
```

1. **上傳**：PDF / DOCX / PPTX / 圖片。
2. **解析**：抽出文字（掃描件要 OCR），找出對應的知識點——用現有的 768 點與
   609 條學習重點做比對，而不是自由生成。
3. **生成**：每個知識點出 2–4 題，合共 10 題，全部附逐步解說。
4. **AI 審核**：見下節。
5. **派發與記錄**：每題存學生的作答、對錯、用時；按班級匯總。

## 六、AI 審核的規則與它的極限

**可以機器判定（必須通過）**

- 數值題 `verify` 重算後等於 `answer`（能抓出算錯的答案）
- 選擇題 `answer` 在選項內；選項內容不重複
- 題幹不重複、不洩漏答案
- 圖是合法 SVG、有 `viewBox`、不引外部資源
- 每題都有逐步解說

**機器判不了（需要語言模型，仍會漏）**

- 語意含糊、兩個選項都講得通
- 題目超出該學習重點，或其實考的是別的知识点
- 情境不適合該年級（用字太深、生活經驗不符）

> 這是 (c) 選「AI 審核」的代價：算錯、抄題這類硬錯可以擋住，但「這題到底對不對」
> 仍然會有漏網。建議在介面上保留「老師可以下架任何一題」的按鈕，成本很低，
> 出事時有補救。

## 七、可見性（(d) 的決定）

| 角色 | 看得到 | 看不到 |
| --- | --- | --- |
| 學生 | 自己的逐題作答、掌握度、改進建議 | 其他同學 |
| 老師 | **自己班級**的逐題作答、分數、掌握度 | 別班學生 |
| 家長 | 總分、薄弱點摘要 | 逐題答案 |

權限要**按班級**判斷，不是「老師就看全校」。學生是未成年人，屬 PDPO 個人資料，
需要同意、保存期限、查閱與更正機制。

## 八、資料模型（草案）

```
users(id, role, name, consent_at)            -- student / teacher / parent
classes(id, name, teacher_id, year)
enrollments(class_id, student_id)
assignments(id, class_id, source, created_at, approved_by)
   -- source: 'lesson_upload' | 'topic_practice'
assignment_items(assignment_id, question_id, order)
attempts(id, student_id, question_id, assignment_id, answer, correct,
         first_attempt, seconds, created_at)
topic_mastery(student_id, topic_id, bank_size, correct_count,
              first_attempt_rate, mastered_at, updated_at)
uploads(id, teacher_id, filename, parsed_topics, status)
```

`attempts` 是唯一的事實來源（append-only），`topic_mastery` 是由它算出來的快照，
可以隨時重建。

## 十、建議建置順序

1. **內容**：先把小學 6,900 題做完（P2–P6 還欠 5,635 題）。沒有題庫，其餘都是空殼。
2. **AI 審核腳本**：`verify` 重算、選項、重複、圖形檢查。不需要後端，現在就能做，
   而且寫題時就能用（邊寫邊驗）。
3. **表格支援**：schema 加 `table`，前端渲染；幾何以外的單元（統計、數據處理）需要。
4. **掌握模型**：先在前端用現有引擎跑，確認「重做只重錯題 + 記錄首次正確率」的體驗。
5. **後端**：帳戶、班級、作答紀錄、權限。
6. **老師上傳迴路**：解析 → 生成 → 審核 → 派發。
7. **改進建議**：把掌握度與先修回溯合起來，講清楚「你這裡錯，因為三年前那個點沒學好」。
